# Contributing

Bug reports and pull requests are welcome. For a security problem, please don't open an issue: see [SECURITY.md](SECURITY.md).

## Building and testing

cam is a Rust CLI, built with stable Rust (edition 2024).

```sh
cargo build
cargo test
cargo fmt
cargo clippy --all-targets -- -D warnings
```

CI runs the same checks on macOS and Linux for each pull request, and both must pass before it merges.

- **Tests never run the real `claude`** or touch your `~/.claude`, `~/.claude.json` or Keychain. The integration tests in `tests/cli.rs` run cam in a sandbox with its own `HOME`, `PATH` and config, and a fake `claude` script that pretends to log in. Unit tests use temporary folders.
- **cam never handles a credential.** It only runs `claude auth login`, `auth status --json` and `auth logout`, and nothing it prints may contain a token.
- **[DESIGN.md](DESIGN.md) is the spec.** A change in behaviour updates it too.

## Pull requests

`main` takes changes through pull requests, merged by squash. Keep each one to a single change, with tests for new behaviour.

The squash commit takes the pull request's title, and that title picks the next version and becomes the changelog entry. So it's a [conventional commit](https://www.conventionalcommits.org/), checked by CI:

| Title | Changelog | Next version, from 0.1.0 | From 1.0.0 |
|---|---|---|---|
| `fix: Keep links when …` | Fixed | 0.1.1 | 1.0.1 |
| `feat: Add …` | Added | 0.1.1 | 1.1.0 |
| `feat!: Rename …`, `fix!: …` | marked breaking | 0.2.0 | 2.0.0 |
| `docs: …` | Documentation | 0.1.1 | 1.0.1 |
| `refactor:`, `test:`, `ci:`, `chore:`, … | left out | 0.1.1 | 1.0.1 |

A breaking change is one that can break someone's setup or scripts: a renamed command or flag, a different config format, or output that scripts read. Write the rest of the title for someone reading the changelog. Commits on your branch can say anything.

Claude reviews a pull request once, when it's opened or marked ready, and comments. The review is advisory, and pull requests from forks don't get one.

## Releasing

For maintainers. [release-plz](https://release-plz.dev) keeps a pull request open titled `chore: release v<version>`. It bumps `version` in `Cargo.toml` and `Cargo.lock`, and adds the release's section to [CHANGELOG.md](CHANGELOG.md), from the titles merged since the last release. It updates itself as more pull requests merge.

1. Read the release pull request. Edit its CHANGELOG section if you like, just before merging, since the section is rewritten whenever another pull request merges. To release a different version than the one it picked (1.0.0, say), change the version in that pull request's `Cargo.toml`, `Cargo.lock` and CHANGELOG heading.
2. Merge it. release-plz publishes the crate on crates.io, through trusted publishing, and pushes the `v<version>` tag.
3. The tag starts the release workflow, generated by [cargo-dist](https://github.com/axodotdev/cargo-dist). It builds macOS and Linux archives, then publishes the GitHub release with the CHANGELOG section as its notes, the install script, and the Homebrew formula in [brunorodmoreira/homebrew-tap](https://github.com/brunorodmoreira/homebrew-tap).
